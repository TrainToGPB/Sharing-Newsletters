# 7가지 설계 원칙

> 원본: [arxiv.org/abs/2605.06651](https://arxiv.org/abs/2605.06651)

[1편](01-overview-and-context/) 의 "워크벤치" 자리잡기를 시스템에 녹이기 위해 저자들이 명시한 7가지 원칙. 추상 슬로건이 아니라 실제 시스템의 어느 구현 결정으로 이어졌는지를 짚는다.

## 원칙 1. 정리 증명으로 환원하지 않는다

**관찰**: Lakatos 식 시각에서 수학 활동은 정리 증명만이 아님. 질문 다듬기·문헌 탐색·수치 실험·이론 구성이 동등한 활동.

**시스템에서**:

- 모든 활동을 일급으로 다루는 sub-agent 들 — 문헌 탐색 전용, 코드 실행 (수치 실험), 정리 증명, 외부 도구 호출
- 어느 활동에 무게를 둘지는 시스템이 미리 정하지 않고 사용자 의도가 결정
- 워크스트림 분기 디자인의 토대 — 한 글이 여러 활동의 병렬 진행으로 풀림

**의미**: 만약 prover + 검증기 두 컴포넌트만으로 디자인했다면 정리 증명에 갇혔을 것. 이 원칙이 시스템 모양 자체를 한 카테고리 위로 밀어 올림.

## 원칙 2. 의도의 점진적 좁힘 지원

**관찰**: 대부분 도메인은 사용자가 처음부터 무엇을 원하는지 안다. 수학은 그 반대 — 발견 과정 자체가 무엇을 풀어야 할지 좁히는 과정.

**근거 인용**:

- 폴리아 *Plausible Inference* — "올바른 질문" 만드는 데 휴리스틱·시행착오 필수
- Cantor — "질문을 푸는 것보다 던지는 게 더 가치 있다"
- AlphaEvolve 사용 경험 — 수학자가 본 작업 전에 작은 변형·관련 문제로 *무엇을 풀지 자체* 다듬는 데 큰 시간 씀

**시스템에서**:

- 단발 호출 인터페이스 아님. 한 Research Question 아래 여러 Goal, 한 Goal 아래 여러 Workstream 동시 가능
- *Initial Exploration* 단계가 명시적으로 존재 — Project Coordinator 가 사용자 첫 발화를 작업 대상으로 받지 않고 되묻고 형식화

**편집자 메모**: 이 원칙은 수학에 국한 안 됨. 사내 LLM 도구 흔한 실패 패턴이 사용자의 첫 자연어 입력을 그대로 작업 대상으로 받아버리는 것. 사용자 자신도 정리 못 한 의도일 가능성이 높은데도. 이 시스템은 그 단계를 인터페이스 안에 끼워 넣음.

## 원칙 3. 네이티브 수학 인공물로 출력

**관찰**: 수학자에겐 표준 작업 형식이 있음 — LaTeX 문서, 마진 노트, 인용 그래프.

**시스템에서**:

- 결과물은 채팅 로그도, 일찍 매끈해진 PDF 도 아닌 살아있는 *working paper*
- 매 step 마다 LaTeX 본문 갱신, 작성과 코멘트가 뒤섞임
- 어느 주장이 어디서 왔는지 마진 노트로 명시 — *"이 pruning 휴리스틱은 사용자 제안에서 나옴; baseline bound 2.2195 는 arxiv.org/abs/… 에서"*

**왜 중요**: 자율 추론 시스템이 사용자 시야 밖에서 비동기로 일할 때 잃기 쉬운 게 *유기적 맥락*. 결과만 받으면 깔끔할수록 약한 부분을 의심할 수단이 없음. working paper 형식이 이 위험을 정면에서 다룸.

## 원칙 4. 비동기 상호작용 + 유연한 개입

**관찰**: 수학 연구는 선형 과정이 아님. 하나의 동기 채팅으로는 받칠 수 없음.

**시스템에서**:

- 메시징 시스템 위에서 여러 sub-agent 가 병렬로 비동기 동작
- 큰 컴퓨트를 한 문제에 쏟아도 사용자가 잠기지 않음
- 사용자는 채팅으로 언제든 끼어들어 방향 변경
- 양방향: 시스템이 막히면 Project Coordinator 가 *먼저 사용자에게 도움을 청함*

**예시**: 코드 sub-agent 가 효율적인 search 알고리즘을 못 찾으면 — *"우리 search 가 충분히 빠르지 않은데 문헌에도 비슷한 예가 별로 없습니다. pruning 전략 직관 있으신가요?"* 가 채팅창에 뜸.

**의미**: *human-in-the-loop* 가 보통 의미하는 "사용자가 옆에서 결과 검토" 보다 한 단계 깊음 — 시스템이 능동적으로 사용자를 호출.

## 원칙 5. 인지 부하의 단계별 노출 (progressive disclosure)

**문제**: 모든 정보를 단일 채팅 스트림에 펴 두면 *"fixed-point 접근으로 가보자"* 같은 고수준 의도와 *"40 라인 measurability 를 verify 해야 한다"* 같은 저수준 실행 로그가 뒤섞여 사용자가 길을 잃음.

**시스템에서**:

- 사용자는 기본적으로 Project Coordinator 와만 대화
- 그 아래 워크스트림 코디네이터·sub-agent 의 sandbox chatter 는 시야에서 가려짐
- 단, 사용자가 원하면 어느 워크스트림이든 어느 sub-agent 든 드릴다운 가능

**핵심**: 인터페이스 구조 = 에이전트 계층 구조. 한 번에 들어오는 정보의 양이 사용자 인지 한도에 맞춰 자동으로 잘림.

## 원칙 6. 불확실성 라이프사이클 (추적·관리·소통)

**관찰**: 수학은 한 lemma 의 흠집이 전체 논문을 무너뜨리는 도메인. 베이스 LLM 추론에는 본질적으로 예측하기 어려운 약점이 있어 zero-shot 출력에 baseline 불확실성 동반.

**시스템에서**:

| 단계 | 구체적 메커니즘 |
| --- | --- |
| 추적 (track) | 버전 히스토리 — 어느 주장이 어떻게 진화했는지, 언제 의문이 제기됐는지 |
| 관리 (manage) | 컴퓨트로 검증 — 리뷰 사이클, 수치 시뮬레이션, 인용 체계적 확인 |
| 소통 (communicate) | 막힌 부분에 인라인 하이라이트·마진 노트 — *"이 부분은 사람이 한 번 봐야 합니다"* 명시 |

**의미**: 불확실성을 *오케스트레이션 대상* 으로 봄. 흔한 LLM 도구의 "맞다 / 모르겠다 / 답하지 않음" 단순 분기와 다름. 모델 출력이 본래 불안정함을 받아들이고 그 위에서 신뢰할 만한 결과를 합성하는 라이프사이클을 디자인.

## 원칙 7. 실패한 시도를 보존

**관찰**: 수학에서 무엇이 안 되는지 아는 게 무엇이 되는지 아는 것만큼 중요. 막힌 골·소진된 전략은 다음 시도의 입력.

**시스템에서**:

- 어떤 골/워크스트림이 실패로 끝나도 조용히 재시작하거나 히스토리 지우지 않음
- 막다른 길은 영구·일급 결과물로 공유 파일시스템에 남음
- *negative space* — 무엇이 안 되었는지의 기록 — 가 다음 워크스트림의 입력으로 흘러 들어감

**철학적 토대**: 다시 Lakatos — *반박이 수학 진보의 근본*.

**편집자 메모**: 이 원칙이 코드·문서 작업에 그대로 차용 가능. 우리가 쓰는 코딩 에이전트는 실패한 시도를 거의 휘발시키는데, 이 패턴을 들여오면 사용자가 *"왜 이 길이 막혔는지"* 를 다음 시도에 직접 활용 가능.

# 시스템 효과와 우리에게의 시사점

이론은 앞 편들에서 정리했다. 마지막 편은 운영자 관점이다. 지금 LLM 을 서빙하거나 임베딩 인덱스를 굴리는 팀에게 TurboQuant 가 어디까지 와 있고, 어떤 조건에서 가져다 쓸 만한지 본다.

## KV 캐시 운영에서의 효과

Google Research 블로그가 내건 두 숫자는 단순하다. KV 캐시 메모리 **6배 감소**, 정확도 손실 **0**. 4-bit TurboQuant 로 키 어텐션을 돌렸을 때 H100 기준 32-bit 대비 **8배 가속**. 어텐션이 메모리 대역폭에 묶여 있는 워크로드라 비트를 줄이면 그 비율이 그대로 throughput 에 반영된다는 점에서 자연스러운 결과다.

다만 사내 운영 결정에는 외부 재현 결과가 더 잡기 좋다. 커뮤니티 재현 구현 (Triton 커널 + vLLM 통합) README 에 적힌 숫자를 그대로 옮긴다.

- **Qwen3.5-27B AWQ 4-bit, RTX 5090 단일 GPU**: prefill 처리량 +5.7%, decode 처리량 +3.1%, 한 시퀀스 최대 토큰 수 2.0배 (457k → 914k), 활성 GPU 메모리 −7.0%.
- **Qwen3.5-35B-A3B MoE, 8× RTX 3090**: 컨텍스트 토큰당 KV 메모리 30.9% 절감, 동일 메모리 예산에서 컨텍스트 길이 1.45배 확장.
- **품질**: needle-in-a-haystack 단일/다중 모두 5/5, 컨텍스트 131k 까지 perplexity 안정.

수치는 GPU 세대, 모델 가중치 양자화 방식, 배치 구성에 따라 흔들린다. 같은 모델을 H100 에서 돌리면 prefill 이득은 더 줄거나 늘 수 있다. 케이스에 따라 차이가 난다는 단서를 깔고 본다.

흥미로운 건 prefill 보다 decode 쪽 이득이다. decode 는 매 스텝마다 누적된 KV 를 다시 읽어야 하기 때문에 메모리 대역폭이 곧 latency 다. 6배 압축은 이 대역폭 압박을 직접 풀어준다. 컨텍스트가 32k 를 넘기면서부터 효과가 두드러진다고 이해하면 맞는다.

## 벡터 검색에서의 효과

TurboQuant 의 두 번째 응용은 ANN/MIPS 인덱스다. 임베딩 벡터를 압축해 RAM 에 더 많이 담거나, 디스크/네트워크 전송량을 줄이는 용도다. 학습형 양자화 (RaBitQ, OPQ, ScaNN 의 SOAR) 와의 비교에서 같은 비트 예산으로 동등한 recall 을 학습 없이 낸다는 점이 핵심이다.

운영 관점에서 이 "학습 없음" 이 갖는 의미는 단순한 편의 이상이다.

- **인덱스 빌드 시간 0**. 데이터 의존 부분이 없으니 calibration 단계가 통째로 빠진다.
- **새 데이터·새 도메인이 들어와도 재학습 안 함**. 임베딩 모델만 바꾸면 끝. 학습형 PQ 는 코드북을 다시 fit 해야 한다.
- **A/B, shadow indexing 비용이 낮다**. 실험 인덱스를 던지고 무를 때 학습 비용이 안 든다.

RAG 시스템 맥락도 짧게 본다. 임베딩 캐시·하이브리드 검색 (sparse + dense) 구조에서는 dense 쪽 인덱스가 자주 갱신된다. 원문 코퍼스가 바뀌거나 임베딩 모델을 업그레이드할 때마다 학습 양자화는 빌드 비용으로 돌아온다. 학습 없는 닫힌형 양자화는 이 운영비를 깎는다. 검색 SaaS 가 아니라 자체 인덱스를 굴리는 팀일수록 차이가 크다.

## 한계와 주의점

마케팅 톤만 보면 "그냥 쓰면 된다" 처럼 들리는데, 재현 구현 README 와 논문 한계 절은 좀 더 보수적이다. 도입 전에 알고 있어야 할 부분들이다.

- **현재는 full-attention 레이어만 압축한다.** 슬라이딩 윈도우 어텐션, linear-attention, Mamba 류는 별도 처리가 필요하다. 최근 모델들이 이런 변종을 섞어 쓰는 경우가 많아 모든 레이어에서 6배가 통하지는 않는다.
- **2-bit 값 양자화는 품질 병목.** 키 3-bit + 값 2-bit 조합의 cosine sim 은 0.94 수준이고, 4-bit 값에서는 0.997 까지 올라간다. 안전 마진을 잡으려면 값에는 4-bit 를 권장한다.
- **prefill 단계 이득은 제한적.** prefill 은 paged KV 할당이 여전히 풀 정밀도로 이뤄지기 때문에 메모리 압박이 양자화 이전에 일어난다. 본 무대는 디코드, 그것도 긴 컨텍스트의 디코드다.
- **하이브리드 디코드 경로의 dequantize 가 일부 float32 로 떨어진다.** 재현 구현 시점 기준이다. 커널이 더 영글면 같은 비트 예산에서 latency 가 더 줄 여지가 있다.
- **MoE 모델은 dense 보다 가속비가 낮다.** 어텐션 외 라우팅·expert FFN 비중이 커서, 같은 압축률이라도 end-to-end throughput 개선폭은 줄어든다. 위에서 인용한 35B-A3B 결과의 prefill/decode 처리량 변화가 27B dense 보다 작은 이유다.

요약하면 "긴 컨텍스트 디코드 워크로드가 큰 dense 모델" 이 가장 잘 맞는 케이스다.

## 다른 접근과의 위치

지금 양자화·압축 풍경에는 비슷한 단어들이 많이 떠다닌다. TurboQuant 가 어디에 끼는지 한 번 정리한다.

- **가중치 양자화 (AWQ, GPTQ, SmoothQuant).** 모델 파라미터 자체를 4-bit 등으로 떨어뜨리는 흐름. TurboQuant 는 가중치가 아니라 **활성화 (KV 캐시)** 와 **인덱스 (임베딩)** 를 양자화하는 쪽이라 직교적이다. 같이 쓰는 게 자연스럽고, 위 재현 결과가 정확히 AWQ 4-bit 가중치 위에 TurboQuant KV 를 얹은 구성이다.
- **Mixed-precision attention (FP8 KV, FlashAttention-3 의 FP8 경로).** 같은 KV 압축 방향이지만 비트는 8-bit 에서 멈춘다. TurboQuant 는 3~4 bit 까지 더 깊게 가는 방향이라 메모리 절감 폭이 크지만, 커널 성숙도는 FP8 경로가 아직 앞선다. 안정성 우선이면 FP8, 메모리 한계 돌파가 우선이면 TurboQuant.
- **학습형 PQ (Faiss 의 IVFPQ/OPQ, ScaNN).** 벡터 검색에서 오랜 베이스라인. 데이터에 코드북을 맞추므로 같은 비트 예산에서 살짝 우위일 수 있다. 학습 시간이 제약이 안 되는 환경 (정적 코퍼스, 분기성 인덱스) 에서는 여전히 유효하다. 반대로 데이터가 빠르게 바뀌거나 다중 도메인을 한 인덱스에 담아야 하는 곳에선 TurboQuant 류가 더 매력적이다.

세 흐름이 서로를 대체한다기보다 각자 다른 축을 누르는 도구다. KV 캐시 비트, 어텐션 커널 비트, 인덱스 코드북 — 어디를 줄이느냐가 다르다.

## 우리에게의 시사점

실무 메모를 짧게 남긴다. 우리 팀이 이걸 자체 모델 학습 없이 가져다 쓸 때의 체크리스트에 가깝다.

- **긴 컨텍스트 (≥ 32k) 인퍼런스 운영팀**: 키 3-bit + 값 4-bit 부터 시도해 본다. needle 테스트와 자체 평가셋을 한 번 돌려 품질 회귀를 확인한 뒤, 같은 메모리에서 컨텍스트를 늘리거나 동일 컨텍스트에서 배치를 늘리는 방향 중 하나를 골라 운영비를 회수한다.
- **vLLM·SGLang·TGI 등 기성 서버 사용 중이면**, 커뮤니티 vLLM 통합 (재현 구현 깃허브) 이 출발점이다. 패치 형태로 들어가므로 자체 빌드 부담이 크지 않다. 단, 슬라이딩 윈도우 레이어가 섞인 모델이면 fallback 경로 동작을 한 번 더 본다.
- **임베딩 인덱스 운영팀**: 학습 없는 압축이라는 점이 가장 큰 운영 이득이다. 임베딩 모델이 분기마다 바뀌는 환경에서는 PQ 재학습 cron 자체를 빼는 그림이 가능하다.
- **자체 모델 학습을 안 하는 팀이라도**, 외부 모델 로컬 서빙의 비용 곡선이 바뀐다는 점은 단기 의사결정에 영향을 준다. 같은 모델을 같은 GPU 에서 1.5~2배 긴 컨텍스트로 돌릴 수 있게 되면, 장비 구매·인스턴스 사이즈 산정 기준이 달라진다. "지금 H100 한 장이 부족한데" 같은 판단을 한 분기 미루는 효과가 날 수 있다.

도입 결정에서 가장 빠르게 확인할 한 가지를 꼽자면, 우리 워크로드가 실제로 디코드 메모리 bound 인지다. prefill 위주의 짧은 컨텍스트 서비스라면 이 모든 이야기가 큰 차이가 안 난다.

## 마지막 한 단락

양자화 SOTA 의 무게중심이 학습형에서 학습 없는 닫힌형으로 이동하는 흐름이 한동안 이어졌다. RaBitQ 가 그랬고, QJL 이 그랬고, TurboQuant 는 그 흐름을 KV 캐시까지 한 번 더 끌고 들어온 사례다. "데이터에 맞추지 않아도 비트 예산을 거의 다 쓸 수 있다" 는 결과는 모델·데이터 갱신 주기가 짧은 운영 환경에 잘 맞는다. 다음 사이클의 양자화 도구도 같은 방향에서 한 번 더 깎여 나올 가능성이 높다.
